# Cross-repository work

`python3 -m nexus work status --registry PATH --json` reads coverage and the ledger without GitHub calls, cloning, migration, or hydration. `run --registry PATH [--repo OWNER/NAME]` captures all open issues through paginated GitHub REST responses, then processes independent items synchronously in bounded repository rounds. No seven-day cutoff applies. Registry configuration is separate from issue obligations; durable tasks, attempts, claims, proof and retry records stay in the existing ledger.

The registry is a JSON object with a `repositories` array. Each entry requires `repo` (canonical owner/name), `path` (absolute local checkout, including offloaded paths), `enabled` (boolean), `executor` (argv), `provider`, `account`, and `verify` (argv for the authoritative verification/delivery adapter). Optional `routes` maps routing labels to executor argv; zero matches uses `executor`, multiple matches fail. Optional `timeout_s` defaults to 600 and is capped at 3600. `max_attempts` defaults to 3 and is capped at 10. Repeated canonical names with identical configuration deduplicate to the first declared path; conflicting configuration fails. Disabled entries remain visible in coverage.

Adapters receive JSON on stdin with the issue, canonical repository, task, stable `idempotency_key`, provider/account, related PR records and `mode` (`build` or `resume`). Provider/account also appear in `NEXUS_WORK_PROVIDER` and `NEXUS_WORK_ACCOUNT`. Related PR candidates are found through the issue timeline. The executor owns product-specific branch, artifact reuse, verification, review and delivery rules. It must use the supplied stable identity for idempotent delivery and inspect existing artifacts before creating a workspace. The core neither clones nor changes a checkout branch. No production deployment or outbound messaging implementation is included.

The verification adapter runs before execution and again afterward. It must query the authoritative destination, independently of executor exit status. JSON states are `absent`, `pending`, or `delivered`. Delivered results require `verified: true`, nonempty `evidence`, and the matching `idempotency_key`. Only that result permits task completion and GitHub closure. A transient API failure, malformed result, missing proof, pending result or unknown state cannot establish delivery. Exit zero alone never completes work.

After an uncertain execution, `absent` also requires `retry_safe: true` before another executor may run. This is a destination-backed assurance that no earlier delivery remains active or applied, not an interpretation of a missing local receipt. Adapters must retain idempotency receipts through outages and distinguish inaccessible destinations from absence. Required external authorization must report pending, never delivered. A crash after delivery is reconciled through the same verification adapter. A closure outage retries only closure once proof has made the task done.

`claim --registry PATH --repo OWNER/NAME ISSUE --pid PID` captures issues and acquires an issue resource for a live direct-session process. `release --registry PATH FLIGHT --pid PID` cancels an unused claim belonging to that process. Executed claims require reconciliation. The same claim primitive serves direct sessions and the work runner. Claims do not expire by time; a competing runner checks owner and recorded executor processes. Tower's script lifecycle leaves work flights to this synchronous runner. Configure the existing scheduler to invoke `work run`; this change installs no schedule or service.

Each failed attempt keeps a log artifact outside temporary workspaces, structured error, attempt count and exponential next-retry time, capped at one day. Independent issues and repositories continue. Executor attempts are bounded; reconciliation remains possible after the execution budget is spent. SQLite transactions serialize claims and intake. A missing local path appears in coverage and execution fails without automatic hydration.

Office's existing Flows source can project these records through `OFFICE_WORK_REGISTRY` and optional `OFFICE_WORK_LEDGER`. Its card includes proven outcomes, current dispositions/reasons and unavailable enabled checkouts; the source includes complete attempts and discovery errors. Historical failures remain available after successful recovery.

Validation uses the existing `npm test` entry point, including subprocess-boundary fixtures in `tests/test_work.py`. Runtime configuration and activation are separate from this code change. The adapter contract is trusted configuration: it must be implemented by the owning product CLI before enabling a repository.

## Eligibility and compatibility

Discovery retains every open issue, including unready/held obligations. Before claiming and immediately before execution, an individual GitHub issue GET must confirm `state=open` and label `ready` or the explicit existing-work obligation `in-pr`. `in-pr` selects resume mode and requires adapter `retry_safe: true` before any executor call. `direct`, `claimed`, `in-progress`, and `in progress` return owned; `hold`, `on-hold`, `blocked`, `cancelled`, and `canceled` suppress execution. Closed issues stay durable but are not executed or presented as proven delivery. A missing discovery-window item gets the same live GET; an API error cannot imply eligibility. Unknown repository selectors fail. These labels are the core contract; product adapters must enforce additional repository-specific authorization and hold rules at their mutation boundary.

PR lookup paginates only the issue timeline and conservatively passes all cross-referenced PR records, including closed/merged candidates. Any candidate selects `resume`; adapters must resolve its authoritative PR state/head and issue relationship, honor PR claims/holds, reuse branches/artifacts, and never create a duplicate. References are candidates, not delivery proof. Unlinked branches/PRs must also be reconciled by the adapter using the stable identity before workspace creation.

Conveyor compatibility: existing `work.item_attempt` events use canonical `repo#item`, source `conveyor`, payload `step`, `status`, `attempt`, `retry_at` (Unix seconds), `evidence` (existing string or structured evidence). The reader compares repo identity case-insensitively and retains the latest event **per step**. Future retry deadlines defer work; started/running/pending/owned/held records require read-only authoritative adapter reconciliation; historical events alone are not active ownership. `succeeded` is process evidence only, never delivery proof. The core exposes these records in status and adapter input, and emits the same envelope with source `work`, step `nexus-work`. Source/step namespaces remain distinct. PR-number conveyor records must be reconciled by the product adapter alongside the referenced PRs; an issue number is not assumed to equal its PR number.

Direct claims do not expire when their process dies: an unused direct claim requires explicit owner release, and any recorded execution requires destination reconciliation. Release refuses client workspaces and non-work flights. It does not release a product branch or remove any workspace. Existing independent resource leases are surfaced as owned without replacement, even after their timestamp.

The verifier is read-only and must return trustworthy destination evidence. Executor adapters must atomically acquire the stable idempotency identity **before any effect**, retain that receipt/workspace through crashes, and check live issue/PR eligibility and all product claims/holds immediately before mutations. `retry_safe=true` must rule out both completed effects and still-running/detached prior executors, including the fork-to-PID-record crash window. Adapters may not infer this from elapsed time or a missing PID. Process-group timeout is bounded locally; adapters must not detach untracked work. Core tests exercise this protocol with temporary subprocess fixtures; they do not certify any product adapter or universal registry activation.

## Source-only handoff

Parent lane owns product adapter implementation, independent acceptance, registry enablement and activation. This source PR does not close #147. No live ledger/plans/registry changes, hydration, deployment, service restart, merge, or outbound messaging are part of validation. Parent must validate each real adapter's atomic identity, authoritative delivery proof, claims/holds, PR reuse, and crash/outage recovery before enabling its repository.

Closed issues with prior executor attempts remain eligible for **read-only proof reconciliation**: an automatic GitHub close during delivery cannot strand a lease after a crash. Proven delivery completes the ledger without another GitHub close; absent proof never permits execution of the closed issue. New closed obligations are retained without implying success.

Office validation here covers the existing card schema and outcome/failure projection through tests. It is not a screenshot or live UI acceptance receipt. Additional product-specific labels, direct-claim stores, branch ownership, review requirements, and authorization must be enforced by each adapter; registry enablement must not precede that implementation.

## Parent review contract repair (PR #148)

`pending` is an unfinished outcome, not a failed attempt. Before or after execution it records `reason`, `evidence`, and `next_retry` in `work.pending`, emits the compatible pending item event, and releases only the core runner claim through its existing cancelled-flight transition. The task remains unfinished. Checking pending never emits `work.executing` or consumes executor budget. Optional adapter `retry_at` is Unix seconds, bounded to 1 second through 1 day from now; omitted/invalid values use 60 seconds. Later checks can finish only with authoritative delivery proof. Historical failures and all artifacts remain retained.

`in-pr` permits source PR reconciliation after `ready` is removed. It does not authorize client default-branch changes, lesson release, or bypass review. Exact PR claims, relationship/head validation, holds and retry safety belong to the product adapter. Core real leases and direct ownership labels still prevent takeover. Historical conveyor held/pending/started events permit verification after current issue holds are released; absent proof requires explicit `retry_safe: true` before execution. A successful process or source PR alone cannot complete a task.

`run --budget-s 300 --max-items 20` exposes bounded defaults (allowed 1–3600 seconds and 1–100 items). Repository rounds select one item per repository before returning to its backlog. Existing `work.serviced` events put least recently serviced repositories first on subsequent invocations. Within a repository, existing work and urgent/p0/p1 labels receive a one-day priority bonus each; creation time supplies aging so old obligations eventually outrank new priority items. Future retry deadlines are excluded from selection capacity. No separate queue is persisted. Discovery, live GitHub checks and adapter processes share the command deadline; each repository turn reserves a proportional share for later repositories. No subprocess launches after its deadline, and in-flight calls are timed out at their remaining allowance (OS cleanup can add small overhead). A 90-repository registry cannot expand this into an hours-long command.

`work.disposition` stores the latest result and reason for read-only status/Office projection, separately from task completion and historical failures. Pending, held (including cancelled source labels), owned, backoff and ineligible obligations remain visible. Status describes the last observed result; it does not call adapters or claim live freshness.

Validation uses temporary GitHub and real subprocess adapter fixtures, including pending before/after execution, existing PR with ready removed, released historical hold versus active owner, fair failure/timeout isolation, future backoff exclusion, aging and Office projection. The separately owned root `_meta/services/nexus-work-adapter.py` is not changed or certified here. No universal activation claim is made.

Selection records current intake dispositions for held, owned and unready obligations before choosing actionable work; these records do not consume `max_items`. Ready/resume obligations and outstanding execution/closure reconciliation keep the aging/urgency ordering. A live eligibility change discovered immediately before execution also leaves the actionable slot available for the next item. Closed obligations without execution uncertainty are recorded once and are not repeatedly queried merely to fill a work budget.

A run limited to one actionable item retains its full remaining execution budget; the budget is divided by the smaller of remaining repository turns and remaining item slots. This avoids reducing an 1800-second one-item run to 20 seconds merely because 90 repositories are registered. Existing work.serviced ordering rotates the next invocation to other repositories; multi-item runs still reserve time for their remaining slots.

After a source executor returns, an authoritative verifier may report `absent` with `retry_safe: true`, the exact idempotency key, a nonempty list of source references with nonblank string `url` and `head` fields, and `resume_kind: review|repair`. This is a verified unfinished pipeline stage: the core records pending and releases its runner claim without recording a failure or closing the issue. The actual executor attempt still counts. A later invocation re-verifies before resuming. Missing evidence, wrong identity, unknown stages, or unsafe retries retain the failure path; executor exit/output alone cannot establish a continuation.
