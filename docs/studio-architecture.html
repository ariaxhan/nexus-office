A. Essential capabilities

Persistent local observation of projects and personal inputs; agent turns that can change files or answer; durable work history; product-specific verification and publication; a place for Aria to inspect, answer, and intervene. These are present across the system, but through multiple implementations.

B. Genuinely shared infrastructure

macOS launchd plus Vaults jobctl/jobrun schedule and prove many jobs; GitHub and Git checkouts are common work surfaces; provider CLIs are reused; the Nexus SQLite ledger is shared by Tower plans and Office task/system views. These are shared in execution, though each application may impose its own rules.

C. Specialized applications

TBS curriculum, family care, Buzz and release evidence; Matra TestFlight feedback, telemetry and app release; Aria’s personal email/feed, Granola, money and research sources; Tradition’s commission and conversation semantics. Their product decisions are specific to those domains.

D. Accidental coupling

Office’s startup wrapper, runtime gate, product board, coordinator list, profiles, sections and feed runner require specific Vaults/TBS/Matra/Tradition paths. A nominally generic Office install has no single config that replaces those dependencies.

E. Accidental duplication

Separate coordinator inboxes and Ask/task queues; multiple CLI provider selectors and fallback policies; separate JSONL/SQLite run histories; several health/recovery loops and output receipts. Distinct product release gates should stay distinguished in this diagnosis.

F. Missing abstraction demanded by existing systems

There is no shared workflow contract connecting intake, ownership, agent selection, durable execution, verification, retry, and Office reporting across TBS, Matra, Tower and personal jobs. This is an observed gap, not a design recommendation.

G. Uncertainty. The audit is a point-in-time inspection. A passing job proof does not establish a user-visible outcome; a running coordinator may finish after capture. I did not exercise destructive actions or externally send/commit anything. Office source had concurrent uncommitted changes during inspection, so some new routes may be newer than the running server. Executor stdout for individual no-change Tower flights was not retained with their terminal events, limiting root-cause attribution. No claim of global Claude↔Codex fallback is supported.

7–8. Fresh Mac and the actual configuration surface

Fresh Mac with one project folder and one provider: the native client can start, but its API default is local port 8790 and fallback is an Aria Tailscale URL (O/app/Office/Model/Api.swift). The shipped service wrapper expects ~/Developer/Vaults, TBS owner configuration, Tradition at 8787, local secrets and launchd/jobctl installation (V/_meta/services/office/office). With only the ordinary folder, Office is not automatically serving. If an engineer starts client/serve.py manually and sets OFFICE_RUNTIME_ROOT, local browsing/search and some Git project tasks can work; empty GitHub credentials mean no populated desks, Watch or actions. Ask still expects a supported authenticated CLI and uses the Office repo as cwd, not the supplied project. Feed has no editorial-inputs DB; TBS/Matra/product sections and Tradition gates are empty/error/irrelevant. Tower has no populated ledger plans or registry. No autonomous workflow starts merely from the folder/provider.

Several inputs → persistent autonomous actions: today that requires a job registration/schedule, input adapters/cursors, work ownership and queue, prompt/context, provider invocation, authorization boundaries, verifier, retry/recovery store, publication destination and an Office projection. The source contains examples of each, but no single install/config path joins them. This is a finding about current behavior, not a proposed implementation.

Conclusion: configuration is scattered across environment, shell, JSON, SQLite, Markdown protocols, plist/job registry and Python/Swift constants. There is no coherent shared configuration model describing a workflow from watched input through permitted action and Office reporting.
